# ٢. مبررات النطاقات المضافة

## لماذا `access/` مستقل؟

سؤال «هل يستطيع هذا المستخدم رؤية/شراء هذا المنتج؟» يستهلكه `catalog` و `cart` و `orders` والبحث. لو سكن داخل `catalog`، لاضطرت كل هذه النطاقات للاعتماد على الكتالوج، ولانتفخ الكتالوج بمنطق أمني ليس ملكه.

مستقلًا: يعتمد على `accounts` + `core` فقط، ويستهلكه الجميع بلا تشابك.

## لماذا `academic/` مستقل؟

السوق الأولي هو الطلاب. الجامعة/الكلية/القسم/السنة + الحزم لها دورة حياة وملكية بيانات خاصة. دفنها في `catalog` أو `customers` يجعلها المصدر الأول للتشابك لاحقًا.

## لماذا `branding/` مستقل ولا يسكن في `core`؟

له موديلات ووسائط (لوجو، أيقونة) و API عام وشاشات أدمن واستراتيجية كاش خاصة. وضعه في `core` يخالف قاعدة «`core` يجب ألا يتضخم».

**تقسيم مهم:**
- `branding/` — كل ما **يراه العميل**: ألوان · لوجو · خطوط · اسم · شعارات · بانرات · سوشيال
- `core/settings` — إعدادات **تشغيلية**: أعلام ميزات · حدود · ضبط قواعد العمل

## لماذا `mailing/` مستقل ولا يبقى في `core`؟

الإرسال صار يقرأ **جداول إعداد**: حسابات وأسرارها ومسؤولياتها وقوالبها
وطابور الصادر والوارد. وبقاؤه في `core` كان يجعل البنية التحتية تستعلم
عن بيانات — وهو بالضبط ما يمنعه اختبار الانتماء إلى `core` أدناه.

والحدّ مع `notifications` سؤالان لا سؤال:

```text
notifications → متى يُرسَل ولمن     (تصنيف · تفضيل · سجل)
mailing       → كيف يُرسَل ومن أين  (نقل · هوية · طابور)
```

⚠️  **و`core/mail.py` نُقل ولم يُغلَّف**: واجهة في `core` تنادي `mailing`
تقلب اتجاه التبعية وتُخفي الدائرة داخل دالة بدل أن تحلّها (ADR-75).

## لماذا `pos/` مستقل — ولماذا لا ينشئ نموذج طلب خاصًا؟

POS **قناة بيع**، لا نظام موازٍ. مفاهيمه الخاصة (جهاز · وردية · صندوق · تسوية نقدية · إيصال) لا مكان لها في `orders`، ومفاهيم `orders` (شحن · تتبع · حالات طويلة) لا مكان لها في POS.

**القاعدة الحاسمة:**
- ❌ **ممنوع:** `POSOrder` منفصل ⟵ تقريران للمبيعات، ومخزونان، ومصدرا حقيقة
- ✅ **مطلوب:** `pos.services.checkout()` يستدعي `orders.services.create(channel=POS)`

## لماذا `finance/` منفصل عن `payments/` و `reporting/`؟

| السؤال | المالك |
|---|---|
| «كيف انتقل المال من العميل إلينا؟» | `payments` — البوابات والمعاملات |
| «كم ربحنا، وأين صُرف المال؟» | `finance` — إيراد · مصروف · تكلفة · صافي |
| «ما اتجاه المبيعات هذا الربع؟» | `reporting` — قراءة وتحليل فقط |

`finance` **يكتب** بيانات (المصروفات تُدخَل يدويًا) — فهو نطاق معاملاتي لا تقرير. و`reporting` لا يكتب شيئًا أبدًا.

# ٣. ملكية النطاق

> لكل قاعدة عمل **مالك واحد**. عند الشك، اسأل: أي نطاق يملك هذه القاعدة؟

| السؤال | المالك |
|---|---|
| هل يستطيع هذا المستخدم شراء هذا المنتج؟ | `access` |
| كم يدفع هذا العميل؟ | `pricing` |
| هل المنتج متوفر؟ | `inventory` |
| هل يصلح هذا الكوبون؟ | `promotions` |
| هل يمكن إلغاء هذا الطلب؟ | `orders` |
| كم عمولة الموظف؟ | `commissions` |
| هل هذا الحساب موقوف؟ | `accounts` |
| ما لون الزر الأساسي؟ | `branding` |
| كم ربحنا هذا الشهر؟ | `finance` |

# ٤. ما ينتمي إلى `core` — وما لا ينتمي

```text
core/
├── models/         TimeStampedModel · SoftDeleteModel · AuditedModel · TranslatableModel
├── api/            BaseViewSet · استجابة موحّدة · pagination · معالج أخطاء
├── errors/         أكواد ثابتة (INSUFFICIENT_STOCK) + ترجمتها
├── permissions/    أوليات الصلاحيات — لا قواعد عمل
├── i18n/           تفاوض اللغة · حقول الترجمة · تنسيق الأرقام والتواريخ
├── money/          نوع Money · الدقة · قواعد التقريب · العملة
├── audit/          AuditLog + الالتقاط التلقائي
├── files/          تجريد التخزين · فحص النوع والحجم · التحكم بالوصول
├── mail/           تجريد الإرسال · SMTP من البيئة
├── settings/       إعدادات تشغيلية — أعلام ميزات · حدود · ضبط قواعد
└── events/         تعريف الإشارات المشتركة
```

## اختبار الانتماء إلى `core`

> احذف نطاقًا واحدًا. هل بقي هذا الكود مطلوبًا؟
> **نعم** ⟵ `core` · **لا** ⟵ ملك ذلك النطاق

## ممنوع في `core` صراحةً

`Product` · `Order` · `Coupon` · `Employee` · `Stock` · أي `*Service` يخص نطاقًا · أي قاعدة عمل.

## البنية الداخلية لكل نطاق

```text
<domain>/
├── models.py           ← ملكية الجداول
├── serializers.py      ← تحقق المدخلات + تمثيل المخرجات + عقد الـ API فقط
├── services.py         ← ⭐ منطق العمل — الواجهة العامة للنطاقات الأخرى
├── selectors.py        ← استعلامات القراءة المعقدة
├── permissions.py
├── api.py              ← views رقيقة
├── urls.py
├── events.py           ← الإشارات التي يبعثها هذا النطاق
├── admin.py
├── tests/
│   ├── test_models.py
│   ├── test_services.py
│   ├── test_api.py
│   └── test_permissions.py
└── README.md           ← الغرض · المسؤوليات · التبعيات · الواجهات · قواعد العمل
```

> **`services.py` هو الواجهة العامة الوحيدة للنطاق.** النطاقات الأخرى تستدعيه ولا تلمس `models.py` مطلقًا.

## تدفق الطلب الإلزامي

```text
API View  (رقيق: تفويض فقط)
    ↓
Serializer  (تحقق المدخلات)
    ↓
Service  (منطق العمل)
    ↓
Model  (الحفظ)
```

**ممنوع:**
- منطق عمل في الـ views (`API → ٥٠٠ سطر منطق`)
- محركات عمل في الـ serializers
- منطق نطاق آخر في الموديلات

## قواعد الـ API

- **التوثيق:** OpenAPI/Swagger لكل endpoint — المصادقة · الصلاحيات · الطلب · الاستجابة · التحقق · الأخطاء · الترقيم · الفلترة · الترتيب
- **الأخطاء:** أكواد ثابتة قابلة للقراءة آليًا + رسائل مترجمة
  ```json
  { "code": "INSUFFICIENT_STOCK", "message": "...", "detail": "..." }
  ```
  **ممنوع** أن يعتمد منطق الواجهة على النص الإنجليزي.
- **الأمان:** كل قاعدة عمل حساسة تُفرض في الباك إند. حراس المسارات وإخفاء الأزرار في الواجهة **لتحسين التجربة فقط**.
- **المعرّفات:** صفر معرّف تسلسلي في أي مسار أو استجابة · `404` موحّد لغير الموجود وغير المملوك · لا كشف للعدّادات — [التفاصيل](06-IDENTIFIERS.md).
- **اللغة:** تفاوض عبر `Accept-Language` ← تفضيل المستخدم ← الافتراضي ← العربية.

# ٧. حدود قاعدة البيانات

قاعدة PostgreSQL **واحدة**. الحدود منطقية لا فيزيائية.

| القاعدة | التفصيل |
|---|---|
| **الملكية** | كل نطاق يملك جداوله |
| **المفاتيح** | **UUIDv7** لكل نموذج يظهر في رابط أو استجابة · `BigInt` للجداول الداخلية عالية الحجم — انظر [06-IDENTIFIERS.md](06-IDENTIFIERS.md) |
| **المفاتيح الأجنبية** | مسموحة عبر النطاقات عند التبرير (`Order → Customer` · `Order → Product`) |
| **الكتابة** | **ممنوعة عبر النطاقات.** `orders` لا يكتب في جداول `inventory` — يستدعي `inventory.services` |
| **المال** | `DecimalField` حصرًا · دقة وتقريب معرّفان في `core/money` |
| **الحذف** | `SoftDelete` للكيانات التجارية · لا حذف فعلي لمنتج بِيع |
| **التدقيق** | `AuditedModel` لكل عملية حساسة |
| **الفهارس** | على كل حقل يُفلتر أو يُرتَّب به · تُراجع مع كل مرحلة |

## ما يُدقَّق إلزاميًا

تغيير الأسعار · تغيير المخزون · تغيير سياسات الوصول · تغيير الأدوار والصلاحيات · التحقق من الحسابات · **إيقاف/تفعيل الحسابات** · الاستردادات · تسويات المخزون · تغيير حالة الطلب · تغيير التارجت والعمولات · تغيير إسناد العملاء · **تغيير بوابات الدفع** · **تغيير الهوية البصرية**.

يُسجَّل: المستخدم · الإجراء · الكائن · القيمة القديمة · القيمة الجديدة · الوقت · IP · بيانات الطلب.

# ٨. الأداء

| المجال | القاعدة |
|---|---|
| **N+1** | ممنوع. `select_related` / `prefetch_related` إلزاميان في كل قائمة |
| **التجميع** | `avg_rate` و `reviews_count` كتجميع لا properties (الخطأ H8 الحالي) |
| **التوفر** | `InventoryService.availability_for(product_ids)` — استدعاء مجمّع واحد لا استعلام لكل منتج |
| **الكاش** | Redis · `branding` مُخزَّن بقوة ويُبطَل عند التغيير |
| **الترقيم** | إلزامي على كل قائمة · لا استجابة غير محدودة |
| **الخلفية** | Celery + Redis للبريد والتقارير والتنبيهات ومعالجة الصور |
| **التزامن** | `select_for_update` + `transaction.atomic` على كل خصم مخزون |

**لا تحسين أعمى.** يُقاس أولًا، ثم يُحسَّن.
