# ١. الحقول المبكرة الإلزامية

> حقول تُخلق في مرحلة مبكرة **رغم أن مستهلكها يأتي لاحقًا**. تكلفتها اليوم أسطر؛ تكلفتها بعد تراكم البيانات = migration مؤلم على أكبر الجداول.

| الحقل | يُخلق في | يستهلكه | تكلفة التأجيل |
|---|---|---|---|
| `AuditLog` | 0.5 | كل شاشات المراقبة | لا سجل لما مضى |
| `Product.requires_prescription` · `regulatory_class` | 3 | الأدوية الموصوفة (مؤجل) | migration على أكبر جدول |
| `StockLocation` | 4 | POS · تعدد الفروع · المخازن | إعادة بناء كل حركات المخزون |
| **`Batch.cost`** | 4 | COGS في المالية | **استحالة حساب الربح تاريخيًا** |
| `Order.channel` | 5 | POS · طلبات الموظفين | كل الطلبات القديمة بلا قناة |
| `Order.location` | 5 | POS · تقارير الفروع | إسناد مبيعات مستحيل رجعيًا |
| `Order.created_by` · `owner_employee` · `commission_employee` | 5 | بوابة الموظفين · العمولات | migration على جدول الطلبات + عمولات تاريخية مفقودة |

> **القاعدة:** الحقل يُخلق ويبقى فارغًا أو بقيمة افتراضية. **لا يُبنى منطقه** حتى مرحلته.

| الكود الحالي | المصير | الوجهة |

| `DeliveryFee` | **MOVE** | `shipping/` |

| `Profile` · `ContactNumbers` | SPLIT | `accounts/` (الهوية) + `customers/` (الملف التجاري) |
| `EmailOrUsernameLogin` | REFACTOR | `accounts/` + فحص `is_active` + معالجة تكرار البريد |

| حسابات التسعير الأربعة المبعثرة | **توحيد** | `pricing/services.py` |

| `products/api.py` (نمط DRF) | REUSE + REFACTOR | نمط سليم · يحتاج queryset واعيًا بالسياسات |
| كل `templates/` و `*/templates/` | ❌ **DELETE** | قرار SPA |
| كل الـ views المرندرة | ❌ **DELETE** | تُعاد بناءً كـ DRF |
| `cart_context_processor` · `settings_context_processor` | ❌ **DELETE** | تصير endpoints |
| `db.sqlite3` (٨.٥ ميجا متتبَّعة) | ❌ **REMOVE من Git** | بيانات وهمية |
| `full-temp/` — SCSS | ✅ **REUSE** | `web/styles/` مع تحويل الألوان إلى CSS Variables |
| `full-temp/` — HTML/jQuery | 📖 **REFERENCE** | مرجع بصري يُترجم إلى JSX |

# ٣. استراتيجية الانتقال

## القرار: كتلة واحدة مركّزة، لا انتقال تدريجي

المتطلبات تطلب انتقالًا **تدريجيًا دون كسر التطبيق القائم**. **نوصي بخلاف ذلك، ولسبب محدد:**

النمط التدريجي (Strangler) قيمته في حماية **مستخدمين وبيانات حقيقية**. لا ينطبق هنا:

| السبب | الدليل |
|---|---|
| لا بيانات تُرحَّل | `dummy_data.py` + Faker — كلها وهمية |
| الواجهة ستُحذف بالكامل | قرار الـ SPA (ADR-03) |
| لا سلوك قائم نحميه | `CreateOrder` و `ApplyCoupon` و `CartUpdate` **لا تعمل أصلًا** (الأخطاء 6-8) |
| إعادة تهيئة DB إلزامية | `AUTH_USER_MODEL` يفرضها مرة واحدة على أي حال |

> **بناء سقالة الحدود على كود ميت أرخص وأسرع من إبقائه حيًا أثناء الهدم.** (ADR-10)

## الجدول التنفيذي — المرحلة 0.5

| اليوم | العمل |
|---|---|
| ١-٢ | نظافة المستودع · إبطال SMTP · `config/` · فصل الإعدادات · PostgreSQL |
| ٣-٤ | `core/` + `accounts/` بـ Custom User ← **إعادة تهيئة DB مرة واحدة** |
| ٥ | حذف كل `templates/` والـ views المرندرة والـ context processors |
| ٦-٧ | فصل النطاقات: `products`→`catalog`+`reviews` · `orders`→`cart`+`orders`+`promotions` · `Address`+`DeliveryFee`→`shipping` · `Settings`→`branding` |
| ٨ | سقالات فارغة: `access/` `pricing/` `inventory/` + طبقة services |
| ٩ | `import-linter` + العقود + `pytest` + CI ← **الحدود تصير مُلزِمة** |
| ١٠ | `README.md` لكل نطاق + مخطط التبعيات |

# ٥. استراتيجية الاختبار

## بنية الاختبارات — تتبع حدود النطاقات

```text
<domain>/tests/
├── test_models.py
├── test_services.py       ← ⭐ الأهم: منطق العمل
├── test_api.py
└── test_permissions.py
```

## التغطية المطلوبة

| الفئة | الأمثلة |
|---|---|
| **وحدة** | الخدمات · الحسابات · المحركات |
| **API** | كل endpoint: نجاح · فشل · تحقق · صلاحيات |
| **أمنية** | وصول غير مصرّح للمنتجات/الموظفين/العملاء · IDOR · تصعيد صلاحيات |
| **تزامن** | منع البيع الزائد · حجز المخزون |
| **مالية** | التسعير · الخصومات · العمولات · P&L |
| **ترجمة** | كل رسالة لها نسختان · تفاوض اللغة |
| **حالات** | كل انتقال مسموح ينجح · كل انتقال ممنوع يُرفض |

## ⚠️ الوضع الحالي

**صفر اختبارات.** كل `tests.py` = ٣ أسطر فارغة. أي إعادة هيكلة بلا شبكة أمان.

**لهذا** يُنشأ إطار الاختبار في المرحلة 0.5 قبل أي بناء ميزات.

# ٦. النشر

| القطعة | التقنية |
|---|---|
| الباك إند | Django + Gunicorn + PostgreSQL + Redis |
| المهام الخلفية | Celery + Redis |
| الفرونت إند | Next.js — بناء ثابت + SSR |
| الوسائط | تخزين كائنات مع روابط موقّعة للملفات الحساسة |
| البيئات | dev · staging · prod — **بمتغيرات بيئة فقط** |

## قواعد

- **صفر سر في الكود.** كل شيء من `.env` / مدير أسرار
- `DEBUG=False` في كل ما ليس dev
- `ALLOWED_HOSTS` صريح
- الـ migrations تُشغَّل كخطوة نشر منفصلة
- استراتيجية تراجع لكل مرحلة: migration عكسي + وسم نشر سابق
