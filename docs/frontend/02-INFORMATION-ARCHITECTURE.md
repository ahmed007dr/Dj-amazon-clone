# ١. القاعدة الجوهرية — ممنوع الصفحات العمودية العملاقة

> **الصفحة الطويلة المفرطة عَرَض معماري، لا مشكلة بصرية.** (ADR-24)

ممنوع بناء ميزة كبيرة كصفحة واحدة طويلة تحتوي كل قسم ونموذج وجدول وإعداد وتقرير وإجراء عموديًا.

عندما تكبر الصفحة أو تحمل أكثر من مسؤولية:

```text
STOP  →  ANALYZE  →  SPLIT  →  DESIGN NAVIGATION  →  THEN CODE
```

**الحل ليس إضافة قسم آخر إلى نفس الصفحة.**

# ٣. العملية الإلزامية قبل أي شاشة كبيرة

```text
1. افحص المعمارية القائمة (المسارات · التخطيطات · المكوّنات · نظام التصميم · الصلاحيات)
2. حلّل الميزة المطلوبة
3. حدّد الأقسام الرئيسية والمسؤوليات المستقلة
4. قرّر النمط: تبويبات · تبويبات متداخلة · شريط جانبي داخلي · مسارات · صفحات تفصيل · Drawers · Wizards
5. اعرض شجرة المسارات/المكوّنات/التنقل المقترحة
6. حدّد المكوّنات القائمة الواجب إعادة استخدامها
7. حدّد المكوّنات القائمة الواجب إعادة هيكلتها
8. انتظر الموافقة قبل تنفيذ تغيير هيكلي كبير
```

## قالب مخرج التخطيط

```text
FEATURE: <اسم الميزة>

CURRENT PROBLEM:
<إن وُجد>

PROPOSED STRUCTURE:
/<route>
├── ...
└── ...

LAYOUT:        <أي تخطيط مشترك>
REUSABLE:      <مكوّنات قائمة تُعاد استخدامها>
REFACTOR:      <مكوّنات تحتاج تعديلًا>
DETAIL:        /<route>/:uuid
CREATE/EDIT:   <مسار مخصص أو Drawer حسب التعقيد>
PERMISSIONS:   <الصلاحيات المطبّقة>
RESPONSIVE:    <سلوك الديسكتوب مقابل الموبايل>
```

# ٦. قواعد لوحات المعلومات

اللوحة **تلخّص**. تجيب: **«ماذا يحدث؟»** ثم التنقل يجيب: **«أين أذهب لأدير ذلك؟»**

| مسموح | ممنوع |
|---|---|
| KPIs · إحصائيات مهمة · تنبيهات · نشاط حديث · إجراءات سريعة · رسوم صغيرة · ملخصات حالة | جداول ضخمة · نماذج كبيرة · إعدادات كاملة · تقارير كاملة · كل إجراء ممكن · كل سجل تفصيلي |

---

# ٧. قواعد النماذج الكبيرة

ممنوع نموذج طويل بعشرات الحقول بلا بنية. استخدم: **أقسام · تبويبات · Accordions · Stepper · مسارات منفصلة**.

| النموذج | البنية |
|---|---|
| إنشاء منتج | Stepper من ٧ خطوات |
| إتمام الشراء | Stepper: عنوان → شحن → دفع → مراجعة |
| إنشاء طلب موظف | Wizard: عميل → أصناف → تسعير → تأكيد |
| إعدادات النظام | شريط جانبي داخلي + حفظ لكل قسم |
| تعديل مصروف | نموذج واحد بسيط — **لا تُعقّده بلا داعٍ** |

---

# ٨. قواعد الجداول

```text
Page Header
    ↓
Summary / KPIs           (اختياري ومختصر)
    ↓
Tabs / Status Navigation
    ↓
Search + Filters + Actions
    ↓
Data Table
    ↓
Pagination
```

**ممنوع** تكديس جداول وإحصائيات ونماذج وفلاتر وتقارير غير مترابطة عموديًا بلا فصل واضح.

# ٩. صفحات التفصيل

إن كان للعنصر تفاصيل مهمة، لا تُجبر المستخدم على التمرير في صفحة قائمة عملاقة.

| التعقيد | الأسلوب |
|---|---|
| تفاصيل غنية ومتعددة الأقسام | **صفحة تفصيل** بمسار خاص + تبويبات |
| تحرير سريع لحقول قليلة | **Drawer** جانبي |
| تأكيد أو إجراء واحد | **Modal** |
| معاينة سريعة دون مغادرة القائمة | **Side Panel** |

# ١١. التخطيطات القابلة لإعادة الاستخدام

تُبنى في المرحلة ١.٥ وتُستخدم في كل مكان:

```text
shared/layouts/
├── DashboardLayout      لوحات النظرة العامة
├── FeatureLayout        قشرة ميزة + تنقل داخلي
├── TabbedLayout         تبويبات رئيسية
├── SidebarLayout        شريط جانبي داخلي
├── ListLayout           رأس + فلاتر + جدول + ترقيم
├── DetailLayout         رأس + تبويبات + محتوى
├── SettingsLayout       شريط جانبي + أقسام بحفظ مستقل
└── FormLayout           Stepper / أقسام
```

> **لا تخترع نمط تنقل جديدًا لكل صفحة.** التطبيق يجب أن يبدو **منتجًا واحدًا**، لا مجموعة صفحات غير مترابطة.

## المكوّنات المشتركة الأساسية

`PageHeader` · `StatCard` · `DataTable` · `FilterBar` · `StatusTabs` · `EmptyState` · `Pagination` · `Drawer` · `Modal` · `ConfirmDialog` · `Toast` · `Breadcrumbs`

**ممنوع إنشاء نسخة ثانية من أي منها.** وسّع الموجود.

# ١٢. علامات الإنذار

عند ظهور عدة علامات معًا، أعِد النظر في المعمارية قبل المتابعة:

- تمرير عمودي مفرط
- أقسام كثيرة غير مترابطة
- أكثر من جدول كبير في صفحة
- أكثر من نموذج كبير في صفحة
- إعدادات مختلطة ببيانات تشغيلية
- تحليلات مختلطة بعمليات CRUD
- سجلات تفصيلية أسفل محتوى ملخّص
- أقسام مكررة
- مكوّن React ضخم
- مئات أو آلاف الأسطر في مكوّن صفحة واحد
- مسار واحد يحمل مسؤوليات كثيرة

---

# ١٣. قاعدة القرار

قبل إنشاء أو توسيع صفحة، أجب:

1. هل تحمل الصفحة أكثر من مسؤولية رئيسية؟
2. هل تصبح طويلة بشكل مفرط؟
3. هل يمكن تقسيم المحتوى إلى مجموعات منطقية؟
4. هل يحتاج المستخدم رؤية كل الأقسام في آنٍ واحد؟
5. هل بعض الأقسام نادرة الاستخدام؟
6. هل توجد إعدادات كثيرة؟
7. هل يجب نقل بعض التفاصيل إلى صفحة تفصيل؟
8. هل تحسّن التبويبات التنقل؟
9. هل يكون الشريط الجانبي الداخلي أوضح؟
10. هل يجب أن تصير بعض الأقسام مسارات مستقلة؟

> **إن كانت عدة إجابات «نعم» — لا تواصل توسيع نفس الصفحة. أعِد تصميم بنية المعلومات أولًا.**

# ١٤. التبويبات ليست حلًا لمعمارية سيئة

```text
❌ Tab 1 = ٢٠٠٠ سطر
   Tab 2 = ١٥٠٠ سطر
   Tab 3 = ٢٥٠٠ سطر
```

إن ضخم التبويب نفسه، فهو يحتاج تفكيكًا إضافيًا: تبويبات متداخلة · شريط جانبي · مسارات · صفحات تفصيل.

**التبويبات لا تُستخدم لإخفاء تكديس كل شيء في صفحة واحدة.**

---

# ١٥. التنقل على الشاشات الصغيرة

**لا تُصغّر تخطيط الديسكتوب فحسب.**

| العنصر | على الموبايل |
|---|---|
| التبويبات | قابلة للتمرير أفقيًا |
| الشريط الجانبي الداخلي | ينهار إلى قائمة منسدلة أو Drawer |
| الجداول الكثيفة | بطاقات أو حاوية تمرير أفقي |
| النماذج الكبيرة | خطوات (Stepper) |
| الإجراءات | قوائم سياقية |

**التسلسل المعلوماتي يجب أن يبقى واضحًا في كل المقاسات.**

تفاصيل نقاط الكسر في [04-RESPONSIVE-DESIGN-SYSTEM.md](04-RESPONSIVE-DESIGN-SYSTEM.md).

---

# ١٦. لا إفراط في الهندسة

الهدف **ليس** خلق تعقيد.

```text
❌ صفحة بسيطة  →  ٥ مسارات + ٤ تبويبات + ٣ متداخلة + شريطان + ٨ Drawers
```

> **استخدم أبسط بنية تُبقي التسلسل واضحًا والصفحة قابلة للصيانة.**

الميزة البسيطة تبقى صفحة بسيطة. صفحة تعديل مصروف لا تحتاج تبويبات.

---

# ١٧. المبدأ النهائي

السؤال ليس:

> «كيف نحشر كل شيء في صفحة واحدة؟»

بل:

> **«كيف نساعد المستخدم على الوصول للمعلومة أو العملية التي يريدها بأقل ارتباك وأقل تمرير؟»**

## الأولويات مرتّبة

1. التسلسل المعلوماتي
2. تجربة المستخدم
3. قابلية الصيانة
4. إعادة الاستخدام
5. الأداء
6. الاتساق
7. إمكانية الوصول
8. الاستجابة

**قبل** تقليل عدد الصفحات أو المسارات.

---

# ١٨. الفرض

هذه الوثيقة **قاعدة معمارية عالمية**. تُستشار عند:

إنشاء ميزة · إنشاء صفحة · توسيع صفحة · إعادة هيكلة تنقل · تصميم لوحة · تصميم CRUD · تصميم إعدادات · تصميم تقارير · تصميم نماذج معقدة · تصميم جداول بيانات معقدة.

> **إن تعارض تنفيذ مطلوب مع هذه القواعد، يُعلَن التعارض صراحةً وتُقترح بنية معلومات أفضل قبل المتابعة.**

## في بوابة الجودة

- [ ] لا مكوّن صفحة يتجاوز حدًا معقولًا من الأسطر
- [ ] كل شاشة كبيرة لها بنية معلومات موثّقة قبل تنفيذها
- [ ] صفر تكرار لمكوّن مشترك قائم
- [ ] كل تخطيط مستخدم من `shared/layouts/`
