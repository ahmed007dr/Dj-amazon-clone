# ٠. قاعدة المسارات — ممنوع ID تسلسلي

> **صفر معرّف تسلسلي في أي مسار.** (ADR-25)

```text
✅ /store/p/stethoscope-littmann-classic-iii     ← slug للكتالوج (SEO)
✅ /account/orders/018f4e2a-9c3b-7d1e-...        ← UUIDv7 لما هو خاص
✅ /admin/accounts/users/018f4e2a-...

❌ /account/orders/1247
❌ /admin/products/89
```

| النوع | المعرّف |
|---|---|
| منتج · فئة · براند · مصنّع · جامعة · كلية | `slug` |
| كل ما عداه | `UUIDv7` |

**رقم العمل يُعرض ولا يُوجَّه به:** الشاشة تعرض `ORD-2026-7K3M9P` والرابط يحمل الـ UUID. البحث برقم العمل يحوّل إلى صفحة الـ UUID.

التفاصيل الكاملة في [backend/06-IDENTIFIERS.md](../backend/06-IDENTIFIERS.md).

# ١. البوابات الخمس

| البوابة | المسار | العرض | الجهاز الأساسي | تستهلك |
|---|---|---|---|---|
| **Store** | `/store/*` | SSR/ISR | الهاتف | `catalog` · `access` · `pricing` · `inventory` (توفر) · `cart` · `reviews` · `academic` · `branding` |
| **Customer** | `/account/*` | SSR | الهاتف | ما سبق **+** `orders` · `customers` · `shipping` · `payments` · `notifications` · `loyalty` |
| **Employee** | `/employee/*` | CSR | التابلت / اللابتوب | `employees` · `targets` · `commissions` · `customers` (المُسنَدون فقط) · `orders` · `catalog` |
| **POS** | `/pos/*` | CSR | التابلت أفقيًا | `pos` · `catalog` · `pricing` · `inventory` · `orders` · `payments` · `customers` |
| **Admin** | `/admin/*` | CSR | اللابتوب / الشاشة الكبيرة | كل النطاقات **+** `administration` · `finance` · `branding` · `audit` · `reporting` |

## الفصل مفروض بنيويًا

```text
app/
├── (store)/       ← route group
├── (account)/
├── (employee)/
├── (pos)/
└── (admin)/
```

الـ route groups في App Router تجعل حدود البوابات **جزءًا من التوجيه نفسه**، لا اتفاقًا شفهيًا.

| القاعدة | التفصيل |
|---|---|
| مكوّنات الأدمن | **لا تصير مكوّنات مشتركة عامة** |
| مكوّنات الموظفين | **لا تلوّث متجر العملاء** |
| المشترك الحقيقي | `shared/` فقط — بعد اجتياز اختبار «مستخدَم في نطاقات متعددة؟» |

# ٢. الطلاب ليسوا بوابة سادسة

> الطالب **نوع حساب** (`AccountType.STUDENT`)، لا بوابة مستقلة. (ADR-18)

| لماذا | الأثر |
|---|---|
| بوابة طلاب منفصلة = نسخة مكررة من بوابة العميل | صيانة مضاعفة لنفس الشاشات |
| احتياج الطالب فرق **محتوى** لا فرق **هيكل** | نفس الملف الشخصي والطلبات والعناوين والفواتير |

## التنفيذ

```text
/account
├── overview
├── orders
├── addresses
├── wishlist
├── academic          ← يظهر لحسابات الطلاب فقط
│   ├── my-university
│   ├── my-faculty
│   ├── required-supplies
│   └── bundles
├── loyalty
└── settings
```

وكتالوج المتجر يتكيّف تلقائيًا عبر `access` + `academic`.

**نفس المنطق ينطبق لاحقًا على الصيدليات والمخازن والتجار: أنواع حسابات تفتح أقسامًا، لا بوابات جديدة.**

# ٣. المتجر — Store

**الأولوية: السرعة و SEO والتصفح من الهاتف.**

```text
/store
├── /                       الرئيسية · بانرات · فئات · مميّزة
├── /c/:category            تصفح الفئة
├── /b/:brand               تصفح البراند
├── /p/:slug                صفحة المنتج
├── /search                 بحث + فلاتر
├── /cart
└── /checkout               ← Stepper
```

## صفحة المنتج — مثال التفكيك الإلزامي

```text
ProductPage/
├── ProductPage.tsx           ← تركيب فقط
├── ProductHeader.tsx
├── ProductGallery.tsx
├── ProductPricing.tsx        ← سعر حسب نوع الحساب
├── ProductAvailability.tsx   ← متوفر · نافد · إشعارني
├── ProductAccessNotice.tsx   ← «هذا المنتج للمهنيين المتحققين»
├── AddToCart.tsx
├── ProductDetails.tsx        ← مادة فعالة · تركيز · شكل دوائي
├── ProductReviews.tsx
└── ProductRecommendations.tsx
```

## متطلبات SEO

عرض من الخادم · بيانات وصفية لكل منتج · بيانات منظمة (Schema.org Product) · روابط دائمة · خريطة موقع · بديل لغوي `hreflang` للعربية والإنجليزية.

# ٦. نقطة البيع — POS

> **استثناء مقصود من قواعد بنية المعلومات.**

POS **ليست** بنية تبويبات. إنها شاشة تشغيل واحدة مُحسّنة للسرعة — الكاشير يحتاج أقل عدد نقرات، لا أفضل تنظيم معلوماتي.

```text
┌────────────────────────────┬──────────────────────┐
│  بحث بالباركود / SKU       │   السلة              │
│  ─────────────────────     │   ──────             │
│                            │   صنف ×٢     ٥٠      │
│   [شبكة المنتجات]          │   صنف ×١     ٣٠      │
│   أزرار كبيرة              │                      │
│   ≥ ٤٤px                   │   ───────────        │
│                            │   الإجمالي   ٨٠      │
│                            │                      │
│                            │   [ دفع ]            │
└────────────────────────────┴──────────────────────┘
```

```text
/pos
├── /                   شاشة البيع
├── session/open
├── session/close       ← تسوية نقدية
├── sales               مبيعات الوردية
├── returns
└── receipts/:uuid
```

## قواعد الواجهة

- تابلت أفقي أولًا · أهداف لمس ≥ ٤٤px · بلا تمرير أفقي
- اختصارات لوحة مفاتيح لماسح الباركود
- الدفع في مشهد واحد — دفع مقسّم بلا مغادرة الشاشة
- حالة الوردية ظاهرة دائمًا

## القدرات الحاسمة

| المجال | القدرة |
|---|---|
| **الحسابات** | إيقاف/تفعيل أي حساب + سبب + **إبطال جلسات فوري** |
| **المراقبة** | من متصل الآن · آخر ظهور · **آخر عملية** · مدة الاستخدام · سجل الجلسات |
| **الهوية البصرية** | ألوان · لوجو · أيقونة · خطوط · شعارات — **بلا إعادة نشر** |
| **بوابات الدفع** | إضافة · تفعيل · إيقاف · ترتيب · حدود — **بلا تعديل كود** |
| **المالية** | إيرادات · مصروفات · أرباح · تدفق نقدي |
| **المعاينة** | معاينة المتجر كأي نوع حساب · معاينة بوابة الموظف بصلاحياته |

## صلاحيات دقيقة إلزامية

> **«أدمن» ليست صلاحية واحدة.**

رؤية الأرباح صلاحية منفصلة عن إدارة المنتجات. تعديل بوابات الدفع منفصل عن إدارة الطلبات. إيقاف الحسابات منفصل عن تحرير الكتالوج.

القسم الذي لا يملك المستخدم صلاحيته: **لا يظهر في التنقل · لا تُجلب بياناته · لا تُرسم عناصره.**

# ٨. الاتساق عبر البوابات

| القاعدة | التفصيل |
|---|---|
| نمط تنقل واحد لكل نوع شاشة | القوائم في الأدمن والموظف والعميل تتبع نفس النمط |
| تخطيطات من `shared/layouts/` | لا تخترع تخطيطًا لكل بوابة |
| مكوّنات من `shared/ui/` | لا نسخة ثانية من `DataTable` |
| **الهوية البصرية موحّدة** | كل البوابات تقرأ نفس متغيرات الثيم من `branding` |

> **التطبيق يجب أن يبدو منتجًا واحدًا، لا خمسة منتجات ملصقة.**
